## Candidate A — local formal producer path

### Existing implementation

`docs/current_status.md` freezes the data-first MVP truth chain as:

```text
PLC / V-PLC event truth
-> Collector acceptance and persistence
-> production_accepted_station_event_fact
-> bounded API contracts
-> OEE / Quality / Trace data semantics
```

`docs/architecture.md` defines the local V-PLC/Collector runtime flow:

```text
V-PLC generates WS01/WS02/WS03 WIP/results
-> DB101/102/103 payload_ready + cycle_valid
-> Collector Snap7 db_read
-> persistence
-> Collector read_done ACK
```

### V-PLC naturally produces station cycles

`s7_plc_sim/app/pipeline.py` initializes `ProductionPlan.active=True`. Its `tick()` continuously starts jobs when the plan is active. On station completion `_finish_job()` increments `cycle_counter`, computes the station result, writes the station payload, and sets:

```text
payload_ready = true
cycle_valid = true
read_done = false
```

The pipeline does not require a manual data seed to start its default continuous production plan. WS01 naturally feeds WS02, and WS02 feeds WS03. NOK/upstream-bypass semantics are generated by the same pipeline.

`s7_plc_sim/app/main.py` continuously calls `pipeline.tick(...)` and exposes DB101/102/103 through Snap7. The legacy simulator drives DB100; station-level production DB101/102/103 is explicitly separated from legacy random-stop behavior. Compose nevertheless declares `s7-plc-sim` dependent on the `simulator` service, so the canonical Compose producer service set includes simulator.

### Collector accepted-only fact writer

`collector/app/services/event_collector.py` only enters the production fact path after:

```text
adapter_decision.disposition == "accepted"
```

It then builds the accepted fact and, inside one storage transaction, calls:

```text
insert_accepted_station_event_fact_no_commit(accepted_fact)
persist_cycle_no_commit(...)
```

`collector/app/services/storage.py` enforces accepted-fact idempotency/conflict checks by `fact_key` and source identity before executing the INSERT into `production_accepted_station_event_fact`.

This is the existing product writer. It preserves the accepted fact's line/plc/station/config/source-event/fingerprint/business-result provenance and does not require a second import contract.

### Decision

```text
LOCAL_FORMAL_PRODUCER_PATH = ACCEPTED / RECOMMENDED
```

Reasons:

- already implemented as the product's production-truth path;
- generates facts through the same adapter acceptance gates used by remote runtime validation;
- preserves local runtime provenance instead of copying another environment's truth into this DB;
- exercises exactly the data-first MVP chain the A1 UI is meant to consume;
- does not require artificial fixture/seed semantics.

## Candidate B — remote accepted-fact copy/import

The API has a bounded read-only `/api/v2/production/accepted-station-events` route that selects only from `production_accepted_station_event_fact`. Repository search found no current product implementation that imports/copies remote accepted-event DTOs back into a local accepted-fact table.

A remote copy would therefore require a new write/import contract, including decisions about:

- preserving or translating `fact_key` / content fingerprint;
- remote `accepted_at` versus local ingestion time;
- source/runtime/config provenance;
- duplicate/conflict semantics;
- whether a remote production fact may be represented as a local production fact.

Those semantics do not exist in the current product path and are not authorized in this task.

```text
REMOTE_ACCEPTED_FACT_COPY = NOT_RECOMMENDED_FOR_CURRENT_A1_LOCAL_SOURCE
REASON = NO_EXISTING_PRODUCT_IMPORT_PATH + LOCAL_REMOTE_TRUTH_MIXING_RISK
```

Remote G5 accepted facts remain valid remote production evidence; rejecting copy as the local producer does not weaken that evidence.
